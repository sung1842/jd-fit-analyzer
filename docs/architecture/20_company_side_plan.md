# 20. 기업(헤드헌터·채용담당) 쪽 기능·화면 구조 (2026-10-28)

> 취지(CLAUDE.md): 스카우트 건 → 후보 탐색 → 핏 분석 → **헤드헌터 승인(HIL)** → 제안. 에이전트는 반복 탐색·분석, 사람은 판단·접촉.
> 연구 근거: [portfolio_insights.md](../portfolio_insights.md), 구직자 쪽 설계 [19](19_app_web_service_plan.md).
> 한 줄: 기업 화면은 "점수표"가 아니라 **스카우트 건 하나를 끝까지 처리하는 작업대**이고, 모든 판단은 **공개 근거 카드**를 눈으로 확인하고 내린다.

## 1. 연구 → 기업 쪽 설계 원칙
| 원칙 | 근거 | 화면에서 |
|---|---|---|
| 점수보다 근거를 먼저 | Spence 신호 / Cui 2025(AI 글 신호 붕괴) | 후보 카드 첫 줄 = 근거 카드 문장 + 배지. 점수는 보조 |
| 신뢰 등급·기록 시점 노출 | Spence, Marlow & Dabbish | 확인됨/첨부/본인주장, "활동 당시 작성"/"회고 입력" 배지 그대로 |
| 같은 기준으로 비교 | Sackett 2022 구조화 면접 | 후보 비교 = 6칸 칸별 나란히 보기 |
| 스킬 중심, 학위 필터 금지 | Harvard/Burning Glass 2024 | 스카우트 건 요건은 "증거로 확인할 역량"으로 입력, 학력은 필수 조건 불가 |
| 정보 부족 ≠ 부적합 | Pallais 2014 | "근거 부족" 후보를 탈락이 아니라 "확인 질문" 대상으로 |
| 사람 승인 없는 접촉 금지 + 설명 | 개인정보보호법 37조의2, 취지 | 제안은 승인 후에만, 후보에게 "추천 근거" 자동 공유 |
| AI 교정 투명성 | Galdin & Silbert | "AI 교정" 라벨 그대로, 기업이 끌 수 없음 |

## 2. 화면 구성 (탭 = 업무 단계 순서)
작업 단위는 **스카우트 건**. 좌측 = 건 목록, 우측 = 선택한 건의 단계 탭.

| # | 화면 | 핵심 기능 | 기존 자산 |
|---|---|---|---|
| 0 | **홈(오늘 할 일)** | 승인 대기 N, 마감 임박 건, 응답 온 제안, 새로 매칭된 후보. 카드 하나 = 바로 처리 버튼 | `desk` 재구성 |
| 1 | **스카우트 건 만들기** | JD 붙여넣기/공고 선택 → `parse_jd` 가 "확인할 역량" 체크리스트 초안 → 담당자가 필수/우대 조정 (학력·나이 필드 없음) | `parse_jd`, `/api/jd/plan` |
| 2 | **후보 탐색** | 에이전트가 사전필터 → 정밀 분석(백그라운드, 진행률). 결과는 3묶음: 근거 충분 / 근거 부족(확인 필요) / 제외. 매칭 제외 요청 후보는 아예 안 나옴 | `search_candidates`, BullMQ, SSE, `match_exclusions` |
| 3 | **후보 검토(핵심)** | 좌: 후보 리스트(근거 카드 수·최고 신뢰 등급). 우: 브리프 = 요건 체크리스트 × 인용 카드(클릭 시 원문 카드), 배지, "근거 없음" 항목은 **면접 확인 질문**으로 자동 변환. 하단: 승인/보류/거절 + 사유 | `brief/[id]`, FitReport `citedCards`, `sourcing/review` |
| 4 | **후보 비교** | 2~4명 선택 → 6칸(상황·역할·행동·어려움·결과·배운 점) 칸별 나란히 + 요건 충족 매트릭스 | 신규 (공개 카드 뷰만) |
| 5 | **제안 보내기** | 승인된 후보만. 템플릿 + "추천 근거 카드" 자동 첨부(후보가 볼 수 있음). 발송은 HIL 상태값, Slack 승인 카드 연동 | `sourcing_actions`, Slack HIL, `notify_slack` |
| 6 | **진행 현황** | 건별 퍼널(매칭→승인→제안→응답→면접), 응답률, 타임아웃(04 문서) | `fit_reports`, `sourcing_actions` |
| 7 | **설정** | 팀원·권한(헤드헌터/채용담당/열람만), Slack 채널, Notion 동기화 | `settings/integrations`, M4 |

## 3. 편의성 구조
- **한 화면에서 판단 완료**: 후보 검토(3)에서 리스트·브리프·승인을 한 화면에. 키보드 `J/K` 이동, `A` 승인, `R` 거절(사유 필수 1클릭 칩).
- **근거 우선 정렬**: 기본 정렬 = 필수 요건 충족 수 → 신뢰 등급 → 점수. 점수 단독 정렬은 옵션.
- **에이전트는 백그라운드**: 건을 만들면 탐색이 큐에서 돌고, 끝나면 홈·Slack 알림. 기다리는 화면 없음 (헌법 2조).
- **확인 질문 자동 생성**: "근거 없음" 요건 → 면접 질문 초안(6칸 형식의 열린 질문). 유도 질문 금지 규칙 공유.
- **Slack 우선 승인**: 이동 중 승인은 Slack 카드(M2), 웹은 상세 판단용. 두 곳의 상태는 같은 `sourcing_actions` 값.
- **설명 책임 자동화**: 승인·거절 사유가 리포트에 남고, 후보에게는 "추천 근거"만 공유 (비공개 기록은 원래 접근 불가 — 공개 뷰만 조회).

## 4. 하지 말 것
- 비공개 기록·`user_memory` 조회, 근거 없는 점수 단독 랭킹, 학력·나이 필터, 승인 없는 자동 발송, AI 교정 라벨 숨김, 후보 글 AI 재작성 요약을 원문처럼 표시.

| 필요 | 상태 |

## 6. 구현 순서 (각 단계 = 루프 개선 한 줄)
| 단계 | 내용 | 루프 개선 |
|---|---|---|
| C1 | 후보 검토 화면(3) 재구성: 브리프에 인용 카드·배지·확인 질문, 근거 우선 정렬 | 핏 분석 결과를 HIL 이 빠르게 판단 |
| C2 | 스카우트 건(`jd_runs` 확장) + 건 목록/홈(0,1) | 스카우트 건 입력 |
| C3 | 요건별 카드 인용 + 확인 질문 스키마 | 핏 분석 품질 |
| C4 | 제안 보내기(5) + 추천 근거 공유 + 열람 로그 | 제안 실행·설명 책임 |
| C5 | 후보 비교(4), 진행 현황(6), 팀 권한(7) | 처리량 확대 |

## 7. 구현 상태
- **C1 (2026-10-28 완료)**: talentfolio `/review` (ProductShell 헤더 "후보 검토").
  - 좌: JD별 후보 리스트, 근거 우선 정렬(충족 요건 수 → 최고 신뢰 등급 → 점수), 점수순은 옵션.
  - 우: 브리프. 에이전트별 충족 요건 × 인용 공개 카드(신뢰 등급·출처·기록일·AI 교정 배지). 철회된 카드는 "공개를 철회한 카드"로 표시. 근거 없는 요건 → 열린 확인 질문(템플릿; LLM 생성은 C3).
  - 승인/거절/보류. 단축키 J/K/A/R, 거절 사유 칩 1~4 + 직접 입력.
  - orchestrator `POST /api/fit-reports/:id/review`: `completed` 도 검토 가능. `reason`(≤200자)·`decidedBy`·`decidedAt` 을 `report.review` jsonb 에 기록 (스키마 변경 없음).
  - 검증: tsc 통과, orchestrator 테스트 40/40 통과. 브라우저에서 목업 응답으로 정렬·단축키·사유 전송·375px 확인. 실 DB 데이터로는 미확인 (현재 fit_reports 비어 있음).
  - 한계: 요건 인용이 아직 tool 단위다(요건별은 C3). 필수/우대 구분은 C2 부터.
