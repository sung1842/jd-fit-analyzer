# 기획자 A의 교차 리뷰 — B(UI), C(UX)

관점: 메시지 명확성 · 제품 취지(에이전트 탐색·분석 → 헤드헌터 승인 → 제안, 지원자는 작업물 축적) 전달 · 섹션 서사.

## B_ui — "종이 위의 포트폴리오, 먹색 위의 한 점 코퍼"
**좋은 점**
- 히어로 카피 "공고 한 줄로 찾아냅니다"는 입력이 얼마나 가벼운지를 한 줄에 담는다. 첫 3초에 이해된다.
- copper로 단일화한 근거(DESIGN.md primary, 블루는 금지 톤과 인접)와 역할별 명도 토큰(`--accent-ink`/`--accent-soft`)이 명확하다.
- 이징 토큰 2개로 통일 → 여러 21st.dev 작가 컴포넌트를 섞어도 일관성이 유지된다.
- 레퍼런스가 개별 컴포넌트 URL 위주(Word Rotate, Text Scramble).

**문제점**
- 히어로 카피에 "사람이 승인한다"가 없다. HIL은 6번 섹션에야 나와서, 앞쪽만 보면 "AI 자동 매칭 툴"로 읽힌다. 취지의 핵심인 역할 분담이 뒤로 밀렸다.
- 숫자 밴드(반전 섹션)가 숫자 3개 모두 "예시" → 대표 반전 섹션이 증거 없는 숫자에 쓰인다. 반전은 메시지(HIL)에 쓰는 편이 더 강하다.
- 워크스루 → 숫자 → 차별점 순서라 "승인"이 워크스루 3단계와 6번에서 두 번 설명된다(중복).
- 지원자 이야기는 마퀴 1줄뿐이다. "왜 여기 작업물을 쌓아야 하는가"가 빠져 있다.

**내 시안에 가져올 것**
- 히어로 서브카피에 "공고 한 줄"이라는 입력 경량성 표현.
- 역할별 명도 토큰 `--accent-ink` (승인 단계 텍스트, AA 대비).
- 이징 토큰 2종 고정 원칙.

## C_ux — "고르고, 만져보고, 바로 시작"
**좋은 점**
- 헤드라인 "AI가 찾고, 사람이 승인합니다" — 취지를 가장 압축적으로 말한다. 세 시안 중 메시지 명확성 1위.
- 기본 역할을 헤드헌터로 둔 이유(B2B 수익 루프가 취지)를 명시했다. 기획 판단 근거가 분명하다.
- 데모가 실제 승인 버튼까지 클릭으로 진행된다 → "사람이 승인"을 말이 아니라 체험으로 전달.
- 상태 설계(idle→searching→candidates→scored→approved), `aria-live` 안내, "데모 건너뛰고 시작" 상시 링크.
- 지원자 모드에서 데모 문구 자체가 바뀐다(같은 루프를 지원자 언어로).

**문제점**
- 히어로 데모와 4단계 워크스루가 같은 이야기를 두 번 한다. 데모를 끝낸 사용자에게 워크스루는 반복이다. 워크스루는 데모가 못 보여주는 것(코드 사전필터, 근거 리포트, 제안 문구)을 맡아야 한다.
- 지원자 쪽 동기("지원하지 않아도 의뢰가 올 때마다 다시 읽힌다")가 섹션 수준으로는 없다.
- 후보 카드 팬은 레퍼런스가 "특정 컴포넌트 미확정"이다.
- 숫자 띠는 B와 같은 문제(전부 예시).

**내 시안에 가져올 것**
- 데모 안 **승인 버튼을 실제로 누를 수 있게** + 완료 토스트 "제안 대기열에 추가됨(예시)".
- "데모 건너뛰기" 링크를 히어로 안에 상시 노출.
- 데모 영역의 `aria-live=polite` 단계 안내.
- 워크스루를 데모와 겹치지 않게: Ch.02에 "코드로 먼저 거르고, 남은 후보만 깊게"를 명시(이미 있음, 강화).

## 세 시안 정리
| | A(서사) | B(비주얼) | C(인터랙션) |
|---|---|---|---|
| 첫 화면에 HIL | 서브카피 | 없음 | 헤드라인 |
| 반전 섹션 용도 | HIL 선언 | 숫자 | HIL |
| 지원자 동기 | 섹션 1개 | 마퀴 | 데모 문구 |
결론: 반전 섹션은 HIL 선언에 쓰고, 숫자는 "예시"로 작게. B·C 모두 지원자 서사가 약하므로 A의 4번 섹션은 유지한다.
